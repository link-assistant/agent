# Release reliability: issue #199

Issue #199 collects #196, #197, and #198 into one pull request. The table below
records every requested behavior, the alternatives considered, and the applied
plan. Each release path and each registry consumer was checked separately.

| Requirement                                                           | Alternatives considered                                                                                  | Applied plan and verification                                                                                                                                                                                                                                                                                                                                                                            |
| --------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| #196: release on protected `main` without a mandatory dedicated token | A fine-grained PAT, a custom GitHub App token, or the built-in Actions token with parent-run attestation | Keep the dedicated token preferred. When absent, use `GITHUB_TOKEN`, prove the generated commit is a direct child of `GITHUB_SHA` and changes only allowed release metadata, create a `Pipeline Status` check on its exact SHA, wait for all required PR checks, and merge only on success. Unit tests cover ordering and fail-closed errors; a real temporary Git repository covers the diff allowlist. |
| #196: validate before release and limit privilege                     | Rely on transitive `needs`, or enumerate the validation jobs explicitly                                  | Both automated and instant release jobs list the validation jobs, block failed or cancelled dependencies, and receive `checks: write` only where needed. Other jobs keep their existing permissions.                                                                                                                                                                                                     |
| #196: support other layouts                                           | Fixed root paths, or unrestricted file patterns                                                          | Root and `js/` package manifests, locks, changelogs, and consumed changesets are supported. `RELEASE_METADATA_PATHS` adds comma-separated exact paths; source or other unexpected changes fail closed.                                                                                                                                                                                                   |
| #197: wait past observed 309–310 second lag without republishing      | Extend the old attempt count, or use a bounded deadline                                                  | Verification now spans about 15.5 minutes, including a check after 310 seconds. The publish command is called once after success. A missing version still fails after the bound; a final registry error reports an unknown state. Regression tests use a no-op clock.                                                                                                                                    |
| #197: avoid stale full-package metadata                               | Cache-control only, random query only, or a per-version document with both                               | Verification, Docker's npm wait, and post-publish polling use version-specific registry URLs with a cache-busting query and `Cache-Control: no-cache`. The install smoke test waits beyond five minutes. All calls remain bounded by step and job budgets.                                                                                                                                               |
| #198: exclude consumed changesets from Prettier                       | `--no-error-on-unmatched-pattern`, or filter staged paths before formatting                              | The staged check uses `git diff --cached --name-only --diff-filter=ACMR -z` and passes existing staged files to Prettier. A real temporary Git repository reproduces a deleted changeset alongside a formatted manifest. The codebase search found no other diff-name list fed into a formatter.                                                                                                         |
| #199: deliver all fixes together and close every issue                | Separate PRs, or one PR                                                                                  | This single PR includes a patch changeset and individual closing references for #196, #197, #198, and #199.                                                                                                                                                                                                                                                                                              |

The existing publish retry path already separates a failed publish command from
read-only registry verification. The release workflow can be rerun after a
temporary registry outage; an already published version enters verification
without publishing the immutable version again. An independent tag creation or
historical backfill job, as explored in the #197 follow-up, would require a
separate policy for unverified or older versions and is not needed to correct
the false-negative verification defect.

## Sources and related components

- [GitHub Actions token](https://docs.github.com/en/actions/security-for-github-actions/security-guides/automatic-token-authentication) and [Checks API](https://docs.github.com/en/rest/checks/runs) support the short-lived installation token and check-run creation.
- [GitHub Actions repository settings](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/enabling-features-for-your-repository/managing-github-actions-settings-for-a-repository) describe the setting that allows Actions to create pull requests.
- [`gh pr checks --required`](https://cli.github.com/manual/gh_pr_checks) waits for branch protection's required check set.
- [`git diff --diff-filter`](https://git-scm.com/docs/git-diff) selects added, copied, modified, and renamed staged paths without deletions.
- [npm registry API](https://github.com/npm/registry/blob/master/docs/REGISTRY-API.md) provides version-specific package metadata. The #197 follow-up measured a `max-age=300` full-package response, so polling that cached document alone is insufficient.
- [Hive Mind PR #2282](https://github.com/link-assistant/hive-mind/pull/2282) and [use-m PR #77](https://github.com/link-foundation/use-m/pull/77) provided related release implementations to compare.
